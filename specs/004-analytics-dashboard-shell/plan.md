# Implementation Plan: Analytics Dashboard Shell

**Branch**: `feature/time-machine-analytics-dashboard-shell` | **Date**: 2026-08-17 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/004-analytics-dashboard-shell/spec.md`

## Summary

Harden the existing React analytics shell around its current route-backed chart registry. The implementation will keep chart views lazy-loaded, make navigation and automatic rotation agree with the URL, enforce safe inclusive date filtering, apply the existing light/dark/automatic theme consistently, and make progress/result notifications accessible, replaceable, and leak-free. The work stays in the listed client files plus focused browser tests; no server, authentication, data-provider, or storage-schema changes are planned.

The codebase-memory graph shows `Main` as the composition root with high fan-out into chart navigation, theme, WebSocket message handling, IndexedDB cache controls, and toasts. `filterDatasetsByDate` has 11 inbound callers, so its behavior will remain a small pure utility with compatibility-preserving validation. `ThemeProvider` owns persistent preference and automatic-mode scheduling, while `toastBus`/`ToastHost` provide the existing decoupled notification boundary.

## Technical Context

**Language/Version**: JavaScript/JSX; Node.js package configured as CommonJS, browser modules bundled by Vite.

**Primary Dependencies**: React 19.2.x, React Router DOM 7.18.x, Vite 8.2.x, Chart.js 4.5.x, `react-chartjs-2`, `chartjs-adapter-date-fns`, Bootstrap 5.3.x, and `suncalc` already present in `package.json`. No new dependency.

**Storage**: Existing browser `localStorage` preferences for theme and chart rotation; existing IndexedDB log/cache behavior is consumed but not redesigned. No new server or database schema.

**Testing**: Playwright 1.62.x using the existing `client/playwright.config.js` and browser fixture patterns. Pure utility behavior may be covered through the existing browser test harness or a focused test that does not add a new test framework.

**Target Platform**: Same-origin React/Vite SPA served by the existing Fastify application over HTTPS; supported desktop and narrow browser viewports.

**Project Type**: Existing full-stack web application; this feature changes only the client analytics shell.

**Performance Goals**: Meet SC-002 and SC-006: filter a 1,000-point, three-series daily dataset within 100 ms in the supported browser; show one updated notification per operation; avoid unnecessary initial chart downloads and avoid timer/listener accumulation.

**Constraints**: Preserve existing chart component props and WebSocket payloads. Do not change authentication, Torn synchronization, IndexedDB schemas, server routes, or domain-specific chart calculations. Use canonical `YYYY-MM-DD` comparison for supported daily labels. Keep route state and visible chart state synchronized. Fail closed to safe loading/empty/error UI when a chart or preference cannot be resolved.

**Scale/Scope**: Existing registry of many independently lazy-loaded analytics views, one authenticated dashboard shell, one shared theme provider, one shared toast host, and shared date-filter utility. The scope covers navigation, shared date controls, theme presentation, notification lifecycle, responsive layout, and focused regression coverage.

## Phase 0: Research and Design Decisions

Research findings are recorded in `research.md`. The important decisions are:

1. Keep route-backed selection as the source of truth for the active chart; derive/clamp the internal index from the route and navigate when rotation advances.
2. Keep date filtering pure and canonical; do not make unsupported weekly/monthly labels look daily.
3. Reuse the existing persistent theme context and shared Chart.js color/options helpers rather than styling individual chart components.
4. Keep notifications decoupled through the existing `EventTarget` bus and use stable keys for progress replacement.
5. Add lifecycle and accessibility checks before changing behavior, and use no new package.

## Implementation Approach

1. **Establish regression coverage** for route navigation, date boundaries, theme cycle/persistence, and notification replacement/cleanup using the existing Playwright setup and lightweight browser fixtures.
2. **Make navigation deterministic** in `main.jsx` and `useChartSlider.js`: normalize invalid route indexes, give controls stable accessible names, synchronize automatic rotation with `navigate`, and ensure no interval survives disable/unmount.
3. **Harden the shared filter** in `dateFilterUtil.js`: preserve non-daily data, handle missing/misaligned inputs safely, enforce inclusive bounds, and return aligned empty datasets.
4. **Unify theme presentation** through `themeContext.js`, `chartTheme.js`, and `useChartTheme.js`: preserve manual preference, deterministic automatic fallback, cleanup scheduled recomputation, and shared readable chart colors/options.
5. **Harden feedback and shell styling** in `ToastHost.jsx`, `toastBus.js`, `main.jsx`, and `index.css`: stable operation replacement, accessible live semantics, safe expiry/dismissal, responsive wrapping, and visible focus/error/empty states.
6. **Verify the feature** with targeted browser tests, `npm run build`, diff/scope checks, and a post-change codebase-memory re-index so future graph queries reflect the implementation.
